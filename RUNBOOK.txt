WOODTEK ERP - SAFETY RUNBOOK (one page, keep in woodtek-erp)
=============================================================

WHAT YOU HAVE
  check-server.bat       read-only health check: folder, database, row counts,
                         /api/health  (double-click on the server any time)
  copy-backups-offsite.bat  copy the newest backups to a USB stick or another
                         PC (remembers the destination after the first time)
  woodtek-snapshot.bat   double-click BEFORE any change -> backups\snapshot-DATE.zip
  woodtek-git-setup.bat  run ONCE -> local git repo + first commit
  backup\backup-woodtek.bat   database backup (schedule it daily)
  start-prod.cjs         the server watchdog (patched v2: no crash-loops)
  woodtek-free-port-3000-v2.bat  run AS ADMIN to stop whatever holds port 3000
  (check-server and copy-backups-offsite arrive on the FACTORY server with
  every install/update; the dev-machine files live in the old PC's copy.)

TWO COMPUTERS (since 2026-10-14)
  FS200 (the Hyper-V VM, 192.168.220.205) is THE factory server: the shop
  works on it every day at http://192.168.220.205:3000 and its nightly backup
  runs there. On FS200 you only ever DOUBLE-CLICK a prepared helper (update
  pack, restore, backup, find-postgres-tools). Nothing is edited, built,
  pulled from git or tested on FS200 - ever.
  The old PC (the one that used to run the shop) is now the DEVELOPMENT
  computer: code changes, builds (build-installer.bat, build-update.bat),
  tests and git all happen there, and its own copy of the app is only a test
  copy - never the company book again.
  Changes travel one way: build the update pack on the old PC -> copy it to
  FS200 -> double-click its apply file -> check the result there.

SENDING AN UPDATE TO THE FACTORY SERVER (the normal way now)
  Small updates: just edit on the old PC, then send a pack. The factory keeps
  working on FS200 the whole time except a 1-3 minute restart while the pack
  is applied - do that at lunch or after hours.
  1. ON THE OLD PC (development machine)
       double-click  update-woodtek.bat    (get the newest code first)
       double-click  build-update.bat
     It builds and packs, and prints the pack name, for example
     dist-update\WoodTek-ERP-Update-20261014-6c1a9f9.zip  (+ a .sha256 next to it).
     Packing never leaves this PC without its own running app.
  2. COPY BOTH FILES TO FS200 (keep them side by side - the .sha256 proves the
     transfer was intact). Easiest with no USB stick: on the old PC open File
     Explorer, click the address bar, type
         \\192.168.220.205\c$\WoodTek-ERP\installer
     press Enter (a login prompt may appear - the FS200 administrator account),
     then paste the .zip and the .sha256 into that folder. A USB stick works
     too if the VM can see it.
  3. ON FS200 (the factory server) - PUT THE NEW APPLY TOOL IN PLACE FIRST
     The apply tool already on the server (built before 2026-10-14) nests
     folders and cannot finish an update - that is exactly what stopped the
     2026-10-14 attempt. The new pack carries the fixed tool; copy it in
     BEFORE applying (only this once):
       a. open the copied .zip (double-click it - Windows shows what is inside)
       b. open the  installer  folder inside it
       c. copy the two files  apply-update.ps1  and  apply-update.bat  into
          C:\WoodTek-ERP\installer\   (click "Replace the files in the
          destination" when Windows asks)
     After this pack is applied once, the tool replaces itself with every pack
     and this step is never needed again.
  4. ON FS200 - APPLY THE PACK
       double-click  C:\WoodTek-ERP\installer\apply-update.bat
     Click Yes on the UAC prompt and wait. It takes a snapshot of .env + data\
     and a database dump into backups\update-...\ first, then applies the pack,
     then waits for /api/health. If the new version does not come up healthy it
     puts the OLD one back by itself. Success looks like:
         "WoodTek ERP is running and healthy" + "Running build: <the pack's>"
     (Every later update skips step 3 - apply-update.bat is already in place.)
  5. VERIFY
       double-click  C:\WoodTek-ERP\check-server.bat
     The row counts must look right (users / machines / orders) and
     /api/health must say 200 OK. Then open the app and check your change.
  IF SOMETHING LOOKS WRONG: the update tool rolls back by itself - when
  anything fails it puts the previous version back and starts it again, and
  the window says "Rolled back successfully". The previous version is also
  kept in backups\update-<version>-<time>\ on the server. Send the agent what
  the apply window said - nothing is lost.
  IF THE APP IS DOWN AFTER AN UPDATE AND DID NOT COME BACK BY ITSELF
  (possible only with an update tool from before 2026-10-14, which had no
  automatic rollback): open C:\WoodTek-ERP\backups\, open the newest
  update-... folder, rename the folder "standalone-old" to "standalone",
  move it into C:\WoodTek-ERP\.next\ (replace anything already there), then
  restart the PC - the app starts by itself. Nothing is deleted by this.
  IF A WINDOW SAYS "Schema sync failed" OR "Cannot find module ... pg":
  that was the 2026-10-14 update tool (fixed since). If the app is running,
  do nothing until the next update; if it is not, use the folder steps above.
  IF THE PACK BUILD STOPS AT "Port 3000 is STILL occupied"
    The build must stop the running WoodTek server to replace the app files,
    and that server runs as a background SYSTEM task - stopping it needs
    administrator rights. The build files now ask for those rights by
    themselves: double-click build-update.bat again and click Yes on the UAC
    prompt (right-click > Run as administrator does the same). If it still
    cannot free the port: open Task Scheduler, right-click the task
    "\WoodTek ERP" and choose End, then run the build again - the build
    starts the app again by itself when it finishes, even if it fails.

THE UPDATE RITUAL (every modification, no exceptions)
  THE EASY WAY (what the old PC - the development machine - does now):
    double-click woodtek-back-to-main.bat   (or update-woodtek.bat)
  Both save any hand-edited files first - a patch copy under
  backups\local-edits-<date>\ plus a "git stash" entry - so the update can
  never stop with "Your local changes would be overwritten by merge"
  (that happened once with hand-edited installer files; it cannot block again).
  Bring an edit back any time with:  git stash list   then   git stash pop
  IF AN UPDATE STOPS ON LOCAL CHANGES ("would be overwritten by merge"):
    double-click  unblock-update.bat  - it shows what is edited, saves a copy to
    backups\local-edits-<date>\local-edits.patch, sets the edits aside with
    git stash, then pulls. Nothing is deleted. (Only needed when the running
    updater is older than 2026-10-14; after this update it does that itself.)
  IF A SCRIPT FAILS WITH A STRANGE PowerShell MESSAGE
    ("The ampersand (&) character is not allowed", "The string is missing the
    terminator", "Unexpected token"): the script FILE on this PC carries one
    of its dashes as a fancy typographic dash, and PowerShell reads a BOM-less
    file in the old Windows codepage, so that dash turns into a quote mark
    that flips the quoting and the error shows up far away from the real line.
    Do NOT try to fix the quotes by hand. The repo was cleaned of these
    characters on 2026-10-14 and the build now REFUSES to pack a script that
    carries one, so the cure is to bring the clean copies onto the PC:
      double-click  update-woodtek.bat
    (if it stops on local changes first, double-click  unblock-update.bat  -
    it shows what is edited, saves a copy to
    backups\local-edits-<date>\local-edits.patch, then pulls). Run the script
    again; if it still fails, send a photo of the window to the agent.
  IF THE UPDATE STOPS WITH GARBAGE LINES OR A FALSE "git pull failed"
    (a line like 'h' or 'vel' is not recognized, then "git pull failed" while
    the lines above it clearly show the pull fetched and fast-forwarded): that
    was the updater replacing its own file while Windows was reading it - a
    .bat file is read by byte position (seen once, 2026-10-14). NOTHING IS
    LOST: the pull really happened and any edits were saved first. Just
    double-click the same file again - it skips the pull and finishes the
    rebuild. Updaters from 2026-10-14 on copy themselves into the Windows temp
    folder first and work from that copy, so this cannot come back; at most,
    the single update that installs that fix may show it one last time.
  THE MANUAL WAY:
  1. Double-click woodtek-snapshot.bat          <- your undo button
  2. git add -A  &&  git commit -m "before change"   (once git is set up)
  3. Apply the new files (copy over the old ones)
  4. node scripts\build-prod.cjs
  5. Restart the server:
       - admin-run woodtek-free-port-3000-v2.bat   (stops old copy)
       - schtasks /Query /FO CSV | findstr /I woodtek   (find task name)
       - schtasks /Run /TN "<task name>"           (start new copy)
  6. Test: sign in as OPERATOR (maroun) and as MANAGER. Both look right?
  7. git add -A  &&  git commit -m "what you changed"

ROLLBACK (something looks wrong)
  1. Unzip the last good backups\snapshot-*.zip over the folder
     (or: git checkout . if using git)
  2. node scripts\build-prod.cjs
  3. Restart the server (step 5 above)

DATABASE BACKUPS
  - The "WoodTek Nightly Backup" task runs backup\backup-woodtek.ps1 at 01:30
    every day: a database dump plus a zip of the data\ folder into
    backups\nightly\.
  - CHECK IT (2026-10-14): that task had been failing - a one-line bug in the
    lock file aborted it before it could write anything, even its log. Fixed
    now, and every failure goes into backups\nightly\backup-woodtek.log.
    Open that log once a week: the newest line must start with OK and show
    "db=... (n MB) data=zipped".
  - Once a week copy the newest dump + data zip to a USB stick or another PC:
    double-click  copy-backups-offsite.bat  on the server (first time it asks
    where to copy - it remembers the answer; see backups\copy-offsite.log).
  - Once a quarter do a test restore on purpose (on the old PC / development
    machine, which has the full source folder: backup\restore-woodtek.bat)
    so you KNOW the restore works before you ever need it.
  - The backup and its restore helpers use only PowerShell 4 features, so they
    also work on the old Windows Server 2012 R2 server.

THE .env RULE
  .env holds DATABASE_URL and AUTH_SECRET = the keys to everything.
  It is in your snapshots and backups. It is NOT in git. Never send it in
  chats or emails. If the PC dies, .env + a snapshot + a DB dump = full recovery.

GIT HABITS (after woodtek-git-setup.bat)
  - Commit after every successful change. Short message, e.g.
      git commit -m "hide admin menus from operator"
  - Push to your private GitHub repo once a week (git push).
  - One source folder only. The stray nested src\src copy is excluded in
    .gitignore; when you are sure nothing needs it, delete it.

OLD WINDOWS SERVERS (Windows 8.1 / Server 2012 R2)
  Node.js 23 and newer refuse to start on those Windows versions and print
    "Node.js is only supported on Windows 10, Windows Server 2016, or higher"
  then exit - nothing runs, and the black window just sits at "Press any key".
  What the installer does now:
  - It starts every candidate node.exe once ("node --version") before using it,
    so it never trusts a runtime blindly again.
  - On Windows 8.1 / Server 2012 R2 it installs Node.js 22 LTS (the newest
    line that officially supports them) - from the zip inside the installer
    when present, from nodejs.org otherwise - and only if that is impossible
    does it fall back to Node.js' own escape hatch,
    NODE_SKIP_PLATFORM_CHECK=1, which the start scripts set on those PCs too.
  If the server still refuses to start on such a PC:
  - Copy runtime\node from a working install (it is one folder, no setup), or
  - set the system variable NODE_SKIP_PLATFORM_CHECK to 1
    (Control Panel > System > Advanced system settings > Environment
    Variables > System variables > New) and start the server again.
  - No script may carry a "#requires -Version 5.1" line: on this old Windows
    the whole script then refuses to run - the nightly backup did that
    silently until 2026-10-14. If any window ever says
    "Requires -Version 5.1", run update-woodtek.bat on the old PC, send the
    new pack to the server, and apply it.
  Keep it honest: Microsoft ended support for Windows Server 2012 R2 in
  October 2023 (no security updates) and PostgreSQL 16 is not tested on it.
  It is fine as a spare PC - a server that runs the shop every day should be
  Windows Server 2016 or newer. In a virtual machine that upgrade is cheap:
  build the VM with a newer Windows Server guest and the workaround is not
  needed at all (and the guest keeps getting security updates).

MOVING THE APP TO A NEW SERVER (or VM)
  DONE on 2026-10-14: FS200 is now the factory server (see TWO COMPUTERS at
  the top). This section stays as the recipe for any future move.
  Two double-clicks, and your factory data moves to the new PC. The old PC is
  never changed by this - it is only read.
  1. ON THE OLD SERVER
       backup\prepare-migration.bat
     Run it from the folder the factory actually uses (the one you update).
     It shows which folder/database it is about to pack and asks you to type
     YES. Then it takes a fresh backup (database dump + data\ zip) and builds a
     folder "WoodTek-Migration" next to the app, with a README inside. Copy that
     whole folder to the new server (USB stick, or the new server's Desktop).
  2. ON THE NEW SERVER
       a. Install first: run WoodTek-ERP-Setup.exe and let it finish.
       b. Then double-click  installer\restore-migration.bat
          It asks you to type YES, then replaces the new server's fresh, empty
          database with the factory data, restores the data\ files, starts the
          service again and prints the row counts of users / orders / machines
          it read back, so you can see the data really arrived.
          If the folder is not on the Desktop: drag it there, or run
          installer\restore-migration.bat -PackDir "D:\WoodTek-Migration"
  3. CHECK, THEN SWITCH
       Sign in with your usual PIN (the users came across), open Orders &
       Dispatch & Assembly, print one job ticket. Only then point the factory
       PCs at the new server (http://<new-ip>:3000) and stop using the old one.
       Keep the old PC switched off-but-intact for a week.
  MANUAL FALLBACK (if the .bat refuses to run)
     - the two files it needs are  WoodTek-Migration\db-*.dump  (the database)
       and  WoodTek-Migration\data-*.zip  (the JSON overlay - dispatch,
       production plans, roles/menus, assembly projects, email settings).
     - database:  "C:\Program Files\PostgreSQL\16\bin\pg_restore.exe"
       --no-owner --no-privileges -d "<DATABASE_URL from .env>" db-....dump
     - data:      unzip data-....zip into  <app folder>\data  (replace it)
     - then start the server again (the "\WoodTek ERP" task) and open it.
  WHAT MOVES, WHAT DOES NOT
     - moves: the whole database (orders, users + PINs, stock, machines,
       audit) and the data\ folder (dispatch state, production plans, material
       progress, roles/menus, assembly projects, email config).
     - moves for reference only: the old .env (as ".env.from-old-pc"). The new
       server keeps its own .env: its own DATABASE_URL and its own AUTH_SECRET
       (that only means everybody signs in once on the new server).
     - does not move: the app code (the new PC installs its own copy), and
       anything you saved outside the app folder.

RUNNING IN A HYPER-V VIRTUAL MACHINE (FS200)
  The app runs fine on a virtual machine, and the Node.js version message is
  about the GUEST Windows version - not about virtualization. Host settings
  that matter:
  - Network: attach the VM to an EXTERNAL virtual switch (Hyper-V Manager >
    Virtual Switch Manager). With the "Default Switch" the VM sits behind NAT
    and the other PCs cannot open http://<vm-ip>:3000.
  - Address: give the VM a fixed IP inside Windows (or a DHCP reservation), so
    the address on shortcuts, bookmarks and printed notes never changes.
  - Memory: 4 GB minimum, 8 GB comfortable - and avoid Dynamic Memory for a
    database server (PostgreSQL wants a stable amount). Set static memory.
  - Start/stop: in the VM settings make Automatic Start Action "Always start
    automatically" and Automatic Stop Action "Shut down the guest operating
    system". A host reboot then brings the app back by itself (the
    "\WoodTek ERP" task starts with Windows).
  - Clock: leave Hyper-V "Time Synchronization" (Integration Services) ON -
    attendance, job timestamps and the nightly backup use the VM clock.
  - Backups: HYPER-V CHECKPOINTS ARE NOT BACKUPS for the database (a checkpoint
    is a crash-consistent disk image, and reverting it throws away everything
    written since). Keep the nightly task running inside the VM
    (backups\nightly), and if you want an image-level rollback point, SHUT THE
    VM DOWN first and then take the checkpoint (e.g. right after a successful
    install or update).
  - One server only: two PCs running the app against two different databases
    are two different company books. Do not let the shop use a fresh install
    until the data question is settled (see the sections above).

IF A SCRIPT SAYS "pg_dump not found" / "pg_restore was not found"
  It means the PostgreSQL command-line tools were not found on this PC.
  FIRST: double-click  backup\find-postgres-tools.bat
  It prints which database this PC uses (host only, never the password), which
  PostgreSQL services are running and where their tools are, and - when it
  finds the tools - offers to write the folder into .env as
  WOODTEK_PG_BIN=<folder>, which the app, the nightly backup, the migration
  pack and the restore all use. Then run the backup / migration again.
  If it finds NOTHING, the database probably runs on another PC (its first
  line says which host). Options then:
    a) install the PostgreSQL command-line tools on this PC (postgresql.org >
       Download > Windows; you can untick the server and keep "Command Line
       Tools"), then run find-postgres-tools.bat again, or
    b) take the migration pack on the PC that holds the database.
  Normal installs need none of this: the scripts search PATH, the registry,
  the running service's own folder, and C:/D:/E:\PostgreSQL (every version
  subfolder).
